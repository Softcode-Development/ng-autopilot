# Writing docs for AI-only development

The project's agent-facing files are the agents' operating manual. No human fills gaps between them, so every file is written for an agent that reads it cold. Apply this whenever you create or edit the project rules, a project doc, a autopilot rule, an agent or a skill.

## Where project knowledge lives

| File | Holds | Never holds |
|---|---|---|
| `CLAUDE.md` | Generated index: what the workspace is, where everything is, how work happens | Anything hand-written — it is regenerated by sync |
| `.claude/rules/project.md` | Product in two lines, the project docs table, the project's hard rules (Rule / Why / Enforcement), do-not-modify list | Descriptions (they live in `docs/`); anything a autopilot rule already says |
| `docs/TECH_STACK.md` | Layer → choice → version → why; frozen packages; non-stack decisions | Tutorials |
| `docs/ARCHITECTURE.md` | Layout, legacy vs new code, state table, project patterns, where things live, i18n setup, testing layout | Generic Angular rules (the autopilot rules) |
| `docs/DOMAIN.md` (+ `docs/DATA_MODEL.md` with a backend) | Glossary, API facts, auth/session facts, entities, wire enums, sensitive data, markets / tenants / roles | Code conventions |
| `docs/DESIGN_SYSTEM.md` | The UI law for new code: catalog, tokens, theme, layout, icons | Generic a11y / motion / visual-gate rules (autopilot `design-discipline`) |
| `docs/FEATURES.md` | Every feature: capability slug, status, requirements | Implementation detail |
| `docs/GETTING_STARTED.md` | Zero → running → working with agents | Rules |
| `.claude/gates.md` | Gate commands, smoke map, visual-gate setup, security triggers | Rules |
| `.claude/<tier>-testing/overrides.md` | Test-tier toolkit, scoped commands, carve-outs | Production-code rules |
| `.claude/plans/` | Active plans and worklogs, the backlog, the archive | Rules that outlive a change |

Every project file holds what **new work** needs. Legacy stays legacy: legacy conventions, the legacy design system and legacy UI-library rules are never written down.

## Each fact lives once

A rule is written in exactly one file; everything else links to it. Two copies of a rule drift apart, and an agent that finds two versions picks one at random. Before adding a rule, grep for the subject; if it exists, extend or link, never restate.

## Anatomy of a rule

Every hard rule carries these parts, so an agent can apply it to a case the author never imagined:

- **Rule** — one imperative sentence, specific enough to check (`No inline template longer than 15 lines`, not `keep templates small`).
- **Why** — the failure it prevents. Agents judge edge cases from the why, not from the wording.
- **Enforcement** — the mechanism: `lint: <rule>`, `hook: <script>`, `static check: <script>`, `CI: <job>`, or `review only`. In a project doc, never claim a mechanism that is not wired; `review only` is an honest answer. In a autopilot rule, it names the mechanism the autopilot tooling ships; the drift check reports a project that has not wired it.
- **Exempt** — the files or cases the rule does not cover (e.g. `*.spec.ts`, the constants file itself).
- **Precedent** — optional: the incident that created the rule (`a spinner was hand-rolled after a faulty node_modules audit`). Precedents stop agents from repeating the same mistake by a different path.

## Decision aids beat descriptions

- Give a **one-sentence decision rule** for every recurring choice (`Did the data come from the API? → server-state library. No → crosses features? → store. No → local signal.`).
- Give **"where things live" tables** so an agent never invents a location.
- Give **audit procedures** before building (`check the upstream catalog first; a node_modules listing does not count`).
- Give **correct-shape examples** in code fences for patterns agents get wrong.

## Owner-only decisions

When a rule can only be changed or lifted by the owner, say so explicitly and say how the lift is recorded (`edit the Status: line to "lifted on <date> by the owner" in the same commit`). An agent may suggest a lift; it stops and asks, never acts on its own judgement.

## Growth slot

Each law doc ends with a "Future rules" section describing how a new rule is appended (source, rationale, why). Rules land there instead of being scattered.

## Hygiene

- No temporal wording (`now`, `recently`, `new in this PR`, `step 12 will…`); the doc states what is true.
- No status that goes stale inside a rule body (`services 3-7 pending`); status lives in plans or the backlog.
- Links are relative and point at a section anchor when the target is long.
